# Trailer Parts B2B Website

Official production release: **v1.0.0** (2026-10-31), from the `axle` branch.
The root `VERSION`, frontend/backend package metadata, Git tag and production image labels identify this release. See [release v1.0.0](https://github.com/zsdadisscy/wanshang/releases/tag/v1.0.0) and the deployment guide for the exact running commit and operating commands.

`frontend/next-env.d.ts` is generated by Next.js and excluded from version control. Development and production builds generate it automatically; CI runs `next typegen` before the standalone TypeScript check.

An SEO-oriented, English-language trailer-parts website based on the included functional plan. It includes a Next.js frontend, Django REST API and Django Admin. PostgreSQL, Redis and the Celery worker are orchestrated with Docker Compose; Python packages are managed by `uv`.

For the Linux deployment baseline and an isolated container verification command, see [Linux deployment](docs/linux-deployment.md).

A complete, separate production stack is available in `deploy/compose.production.yml`, with a private ClamAV service, ASGI API, production frontend, HTTPS ingress and guarded startup/backup/restore scripts. Its private configuration is `deploy/.env.production`, generated once by `python deploy/configure.py init --import-existing`; the repository-root `.env.production` remains an older mail/Turnstile overlay. See [production deployment operations](docs/linux-deployment.md#完整生产栈与运维脚本) before starting services. The production stack does not reuse the development or preview database volumes.

For the latest independent source recheck, additional fixes, validation evidence and outstanding launch requirements, see [Security recheck (2026-10-24)](docs/security-recheck-2026-10-24.md). The [earlier security review](docs/security-review-2026-10-24.md) records the initial fixes and evidence.

For the exploitability assessment of the remaining 15 High container findings and the conditional release recommendation, see [Security risk assessment (2026-10-24)](docs/security-risk-assessment-2026-10-24.md).

For the subsequent native-runtime replacement and new verification evidence, see [Native security remediation (2026-10-24)](docs/security-remediation-2026-10-24.md).

## Quick start

1. Copy `.env.example` to `.env`. Keep `DJANGO_ENV=development` locally. The example values are deliberately rejected by production safety checks.
2. Start infrastructure and the worker:

   ```powershell
   docker compose up --build -d
   ```

3. Set up and migrate the Django API:

   Use `uv` 0.13.5 or newer and the Python 3.13.18 runtime pinned by `backend/.python-version`. For an older `uv`, prefix these commands with `uv tool run --from uv==0.13.5 uv` in place of `uv`. Unix hosts also need a maintained system `libpq` (for example, `libpq5` on Debian/Ubuntu); Windows development uses the default `dev` dependency group for its binary wheel.

   ```powershell
   cd backend
   uv python install 3.13.18
   uv sync --locked
   uv run python manage.py migrate
   uv run python manage.py configure_wanshang
   uv run python manage.py createsuperuser
   uv run python manage.py runserver
   ```

4. Start the frontend in a second terminal:

   ```powershell
   cd frontend
   npm ci
   npm run dev
   ```

Open [http://localhost:3000](http://localhost:3000), API at [http://localhost:8000/api](http://localhost:8000/api), and Admin at [http://localhost:8000/admin](http://localhost:8000/admin).

The website itself uses the backward-compatible raw `/api` endpoints configured by `API_BASE_URL` and `NEXT_PUBLIC_API_BASE_URL`. External integrations should use `/api/v1`, which returns the documented `{ success, data, message }` envelope; do not point the browser client at `/api/v1` without retaining that envelope contract.

Consent-aware attribution is stored through `POST /api/visit-sessions/`,
`POST /api/page-views/`, and `POST /api/events/`. RFQ and contact submissions
link the same opaque `session_id` to first/last-touch, UTM term/content,
referrer, and landing-page data without retaining the raw client IP.

Public content is available from `GET /api/news/`,
`GET /api/news/{slug}/`, `GET /api/banners/`, and
`GET /api/site-settings/`; the same routes are available below `/api/v1/`.
Product detail responses include ordered, typed gallery images with required
ALT text. Draft or scheduled news articles and inactive/expired banners
are never returned by public endpoints.

The About page can be maintained in Admin under **Company profile**, including
the introduction, business role, products, markets, strengths, quality information,
search metadata and ordered photos with ALT text. New profiles are drafts; add
verified information before enabling **Is published**. Unpublished content is
excluded from `GET /api/company-profile/` and `/api/v1/company-profile/`.
Site settings also expose the brand tagline, map link and LinkedIn link; changes
reach the frontend through its normal 60-second data revalidation.
Staff editors need the corresponding Company profile and Company photo
permissions; existing staff groups are not granted new permissions automatically.

The supplied WANSHANG company identity and product families are maintained in
`backend/catalog/company_data.py`. After applying migration `0021`, use
`uv run python manage.py configure_wanshang --dry-run` to validate and
`uv run python manage.py configure_wanshang` to apply them. The command updates
the company settings and published manufacturer profile and creates or updates
six categories covering all three supplied catalogue groups. It creates no
product models or technical specifications and preserves unrelated settings,
photos and categories. It replaces the supplied profile fields on each run;
edit the CMS directly for subsequent company changes. Markets are proposed
target regions, not a claim of existing exports. The current role is
Manufacturer; Admin also supports Manufacturer and trading company for later use.
Starter catalogue fallback is disabled by default. `seed_demo` is only for
isolated demonstration databases and must not populate the company catalogue.

Browser RFQ, single-product inquiry and Contact forms retain a version-4 UUID
`Idempotency-Key` across retries of unchanged business content. The API returns
the original reference for an accepted retry without creating another lead or
notification; reusing the key with different business content returns HTTP 409.
Challenge tokens and source attribution may change during a retry. Uploaded file
bytes are part of the content fingerprint. Only keyed hashes are stored on the
lead, not the raw identifier or a second copy of the request. External clients
may use the same header; clients without it retain the previous submission
contract. Migration `0020` must be applied before running this API version; the
production start/update scripts apply it through the normal guarded workflow.

## Useful commands

```powershell
# Apply the supplied WANSHANG company identity and product categories.
cd backend; uv run python manage.py configure_wanshang

# Run backend checks.
cd backend; uv run python manage.py check; uv run python manage.py test

# Rescan quarantined RFQ files, or replay persisted broker failures.
cd backend; uv run python manage.py scan_attachments
cd backend; uv run python manage.py replay_notifications

# Verify frontend types, lint rules and the production bundle.
cd frontend; npm run typecheck; npm run lint; npm run build

# Run focused frontend security regression tests.
cd frontend; npm run test:security

# Stop infrastructure without deleting database volumes.
docker compose down
```

The compose file is a local-development stack: it intentionally exposes PostgreSQL and Redis on localhost. Do not expose these ports publicly in production; put Django/Next behind HTTPS reverse proxying and use managed/private database and cache services.

The host API uses `DJANGO_CACHE_URL`; the container worker uses the internal Redis service by default. Set `CELERY_CACHE_URL` only to override the worker cache with a container-reachable address.

Compose passes database and Redis credentials as raw components so passwords containing URL-reserved characters still work. Optional `CELERY_DATABASE_URL`, `CELERY_REDIS_URL`, and `CELERY_CACHE_URL` overrides must be fully URL-encoded. The worker receives the HTTPS, public-media, Turnstile, and attachment-scanner settings from `.env`; keep the scanner command available inside the worker image. On Linux hosts, bind-mounted media directories must be writable by the container's UID/GID `10001:10001`.

PostgreSQL 16.15 and Redis 7.4.11 are pinned to verified official image digests for amd64 and arm64. Applying an image update requires pulling and recreating the corresponding services, then checking their running versions; changing this file does not update existing containers.

The backend requires Python 3.13.18 or a later 3.13 security release and Django REST framework 3.18.x, starting at 3.18.3. DRF 3.18 changes `many=True` validation errors from lists to dictionaries; this project sets `REST_FRAMEWORK['LIST_SERIALIZER_ERRORS_AS_DICT'] = False` to preserve the existing API contract. DRF plans to remove that compatibility setting in 3.20, so review client error handling and the API contract tests before upgrading beyond 3.18. Install the committed lockfile rather than reusing an older virtual environment.

The worker image pins official Python 3.13.18 Alpine 3.24 and `uv` 0.13.5 manifests by digest. A separate builder compiles the locked Pillow source with PNG/JPEG/WebP native support and the `container` extra's psycopg C binding. The final stage contains the maintained system libraries and application sources, with no compiler, libstdc++, Kerberos/GSS, Perl or ACL toolchain. After updating code or locks, rebuild and recreate the worker, then verify the running container:

Before updating an existing installation, back up its database and compare its applied migration history with this checkout. Reconcile any divergent migration branches before running migrations or recreating application containers; do not use `--fake` to hide the difference.

```powershell
docker compose build --pull celery
docker compose up -d --force-recreate celery
docker compose exec celery uv run python -c "import sys, rest_framework; print(sys.version); print(rest_framework.VERSION)"
```

Apply the same runtime and lockfile update to the separately deployed Django API and restart it. Confirm Python and DRF versions on the actual API and worker hosts; a successful local test or registry-manifest check does not confirm a running deployment. Container builds and smoke checks require a running Docker daemon.

The default container runs `PSYCOPG_IMPL=c`, linking its locally compiled psycopg binding to Alpine's system libpq 18.6 and OpenSSL 3.5.9. It does not use a binary wheel's private SSL libraries. The lockfile's `container` extra is installed in the builder with `uv sync --locked --no-dev --extra container`; do not copy the build environment from Windows or install compiler packages in the final runtime. Independent host installations need their own maintained runtime and native-dependency verification; the container's security conclusions do not automatically apply to them.

The final image uses Alpine zlib `1.3.2-r1`, including the CVE-2026-85091 patch. Pillow's optional TIFF/JPEG2000/AVIF, color-management, font and X11 native components are disabled; untrusted image attachments select the expected PNG/JPEG/WebP decoder before parsing. PDF and CAD validation remains supported. This minimal libpq build omits GSS/Kerberos client authentication and LDAP connection-service discovery; server-side LDAP password authentication does not require client libldap. Use the configured password/TLS connection. Adding native codecs, authentication plugins or a malware engine requires a derived-image scan and functional verification.

The worker drops all Linux capabilities and enables `no-new-privileges`. `config/runtime_security.py` checks the final image's actual package versions, loaded libraries and PNG/JPEG/WebP round-trips during the build. The `linux-runtime` CI job also checks effective restrictions, the full PostgreSQL test suite, Redis, notifications and attachment quarantine in a disposable Compose project, then runs Grype against the verified image. High/Critical findings, including those without a published fix, fail CI. Run the same integration check locally from the repository root:

```bash
python3 scripts/check_linux_stack.py --output-dir output/linux-check
```

Local SVG illustrations are development-only starter content. Production catalogue, banner and application media must come from verified CMS uploads or the approved HTTPS object-storage/CDN host configured with `NEXT_PUBLIC_IMAGE_HOSTNAME`; absent production media is shown as an explicit empty state rather than substituted with demo photography.

The starter images and business copy are illustrative. Replace all contact details, testing claims, certifications, pricing, delivery claims, and product specifications with the company’s verified material before publishing.

## Production checklist

The application now fails closed when `DJANGO_ENV=production`: `DEBUG=True`, a short/example secret, wildcard or non-public hosts, non-HTTPS/credentialed public origins, missing HTTPS/proxy configuration, a non-SMTP email backend, invalid public sender/recipient addresses, conflicting or disabled TLS/SSL settings, or invalid SMTP connection bounds will stop Django during startup. The frontend production build likewise requires a public HTTPS `NEXT_PUBLIC_SITE_URL` origin and `NEXT_PUBLIC_API_BASE_URL`; local, literal-IP, credentialed or malformed public URLs stop the build.

Before deployment:

Request bodies have a hard 38 MiB limit, including multipart overhead and Admin
formsets. RFQ multipart parsing additionally stops at 10 MiB per file, 25 MiB
across all file parts, or five files, returning HTTP 413 and removing temporary
uploads. Every file field counts toward these limits. ASGI applies the total
body limit before Django buffers the request, including chunked requests and
missing or understated Content-Length headers; its per-file checks run during
the subsequent multipart parse. Configure the ingress proxy with an equal or
smaller request-body limit (for Nginx, `client_max_body_size 38m;`) and split
larger Admin batches across requests. Restart the API after deploying these
changes; the ASGI deployment must use `config.asgi:application` so the outer
body limiter is active.

1. Set a unique `DJANGO_SECRET_KEY` of at least 50 characters, `DJANGO_DEBUG=False`, explicit public hostnames in `DJANGO_ALLOWED_HOSTS`, credential-free public HTTPS origins in `DJANGO_CORS_ORIGINS`, and either HTTPS redirect or a trusted TLS-terminating proxy. Wildcards, URL-shaped host entries, loopback/private literal IPs, HTTP origins, credentials, paths, queries and fragments are rejected.
2. Configure `DJANGO_NUM_PROXIES` to the exact number of trusted reverse proxies. Form throttles use separate IP and email limits, attachment-bearing RFQs also use an independent stricter upload-IP bucket, and all counters share Redis through `DJANGO_CACHE_URL`. Public API quotas use an atomic Redis sliding window so concurrent workers cannot spend the same slots. Cache errors reject the request with HTTP 503 before writes or notifications. In addition to ordinary cache commands, custom ACLs must permit `EVAL`, `TIME`, `ZREMRANGEBYSCORE`, `ZCARD`, `ZRANGE`, `ZADD` and `PEXPIRE` for the application's namespaced keys. The new `:atomic-window:v1` keys deliberately start fresh quotas on deployment; older list keys expire naturally. Gateway connection/rate/body limits remain necessary before application processing. If that trusted edge injects GeoIP headers, set their WSGI names (for example `HTTP_CF_IPCOUNTRY`) in `DJANGO_GEOIP_COUNTRY_HEADER`/`DJANGO_GEOIP_CITY_HEADER`; they are rejected unless proxy mode is enabled. Device, browser, and operating-system labels are derived server-side from the User-Agent rather than trusted from public payloads.
3. Configure the exact SMTP backend, a host and credentials, public-domain `DEFAULT_FROM_EMAIL`/`SALES_NOTIFICATION_EMAIL` addresses, a port from 1–65535, and a positive finite `EMAIL_TIMEOUT`. In production, enable exactly one of `EMAIL_USE_TLS` (STARTTLS) and `EMAIL_USE_SSL` (implicit TLS); disabling both is rejected to prevent credentials and inquiry contents being sent over plaintext SMTP. Both flags accept only `True` or `False`. The Celery worker sends both sales notifications and customer confirmations, records delivery timestamps/failures, and avoids resending completed messages during retries. Notification tasks deliberately ignore unused Celery results so an unavailable result backend cannot block form responses. Keep the positive `CELERY_REDIS_SOCKET_CONNECT_TIMEOUT`, `CELERY_REDIS_SOCKET_TIMEOUT`, `CELERY_TASK_PUBLISH_MAX_RETRIES`, and `CELERY_TASK_PUBLISH_RETRY_INTERVAL` values within the request-latency budget; bounded publish failures are persisted for `replay_notifications`.
4. Set `DJANGO_PUBLIC_BASE_URL` to the credential-free public HTTPS API base, configure `NEXT_PUBLIC_SITE_URL` and `NEXT_PUBLIC_API_BASE_URL`, and set `NEXT_PUBLIC_ENABLE_STARTER_FALLBACK=false`. Production pages will not resurrect demo products when the API returns 404 or is unavailable.
5. Before migrating an existing database, replace any CMS external media, document or WhatsApp URL that is not credential-free HTTPS. Migration `0014` reports the affected model/record IDs and stops instead of publishing an unsafe legacy URL. Then run `uv run python manage.py migrate` and `uv run python manage.py collectstatic`. Migration `0002` initially copies existing RFQ attachments from public media into `private_media`; migration `0016` now performs a full fail-closed preflight, moves public-only files—including orphaned files left under the dedicated public `quarantine/rfq` namespace after database rows were deleted—into private storage, removes only hash-identical public duplicates, accepts private-only files, and never republishes them on rollback. Any missing, conflicting, linked, reparse-point, non-regular or path-escaping RFQ entry stops `0016` before file changes. Migration `0015` similarly moves uploaded product documents out of public media and fails closed on missing, conflicting or path-escaping legacy records.
6. Mount `backend/private_media` as private persistent storage. Do not expose it through a web server. Customer RFQ files are downloaded only through the authenticated Admin endpoint; published product documents are delivered only through the status-checked API download endpoint after extension, size and signature revalidation.
7. Install ClamAV (or a command with ClamAV-compatible exit codes) and set `ATTACHMENT_SCANNER_COMMAND`, for example `clamscan --no-summary`. The application appends the private file path as the final argument. Exit code `0` marks a file clean, `1` marks it infected, and every other result remains quarantined. Production never honours `ATTACHMENT_ALLOW_UNSCANNED_IN_DEVELOPMENT`; with no working scanner, uploads are retained privately but Admin download returns `423` until `scan_attachments` reports them clean.
8. Create a Cloudflare Turnstile widget, set `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`, and keep the widget actions exactly `rfq` and `contact`. Django verifies every token with Cloudflare's Siteverify endpoint and checks the matching action. Production also requires the returned hostname to belong to `DJANGO_CORS_ORIGINS` or `DJANGO_ALLOWED_HOSTS`, and rejects a missing secret or a public Cloudflare testing secret at startup. Both public form endpoints fail closed if verification cannot run. `TURNSTILE_REQUIRED=True` enables required verification outside production.
9. Keep `ADMIN_LOGIN_MAX_FAILURES` and `ADMIN_LOGIN_FAILURE_WINDOW` appropriate for your operations. Admin login attempts reserve shared-cache limits atomically before password verification, including parallel attempts; successful logins clear the corresponding counters. The Redis cache uses a fixed Lua counter script to preserve expiry, so custom Redis ACLs must permit `EVAL`, `EXISTS` and `INCRBY`. `DJANGO_NUM_PROXIES` determines whether forwarded addresses can be trusted.
10. Set `DJANGO_PUBLIC_MEDIA_URL` to the credential-free public HTTPS origin used for public Admin uploads and allow the same hostname in `NEXT_PUBLIC_IMAGE_HOSTNAME`. Production rejects relative, HTTP, credentialed, loopback/private-IP, queried or fragmented media URLs. Back that origin with object storage/CDN or a persistent media volume served by the trusted reverse proxy; never route the separate `private_media` RFQ store through it.
11. Use database backups, monitored malware scanning for CAD uploads, and an HTTPS reverse proxy. The included Compose file remains a local infrastructure/worker stack, not a complete production ingress definition.

If attachment scan publication fails because the broker is unavailable, files stay privately quarantined and the request does not run the scanner synchronously. Monitor pending/error attachments and run `scan_attachments` after service recovery; an unscanned file remains unavailable for download.
